# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

A German-language recipe/meal-planning PWA ("Rezepte") built with TanStack Start, React 19, and Supabase. Managed via [Lovable](https://lovable.dev) — the connected git branch syncs back to the Lovable editor, so avoid rewriting published history (force-push, rebase/amend/squash of pushed commits) and keep the branch in a working state.

## Commands

- `bun run dev` — start the dev server (Vite + TanStack Start)
- `bun run build` — production build
- `bun run build:dev` — development-mode build
- `bun run test` — run the full test suite (Vitest, `run` mode — no watch)
- `bun run test -- src/lib/meal-plan.test.ts` — run a single test file
- `bun run test -- -t "test name"` — run tests matching a name pattern
- `bun run lint` — ESLint over the whole repo
- `bun run format` — Prettier write (100 print width, double quotes off, trailing commas)
- `bun run preview` — preview a production build

Package manager is Bun (`bun.lock`, `bunfig.toml`). `bunfig.toml` enforces a 24h supply-chain guard (`minimumReleaseAge`) on new dependency versions — only a short allowlist of `@lovable.dev/*` packages bypasses it; adding to that list needs explicit user confirmation.

## Architecture

### Stack

TanStack Start (file-based SSR router on Vite/Nitro) + React 19 + TypeScript + Tailwind v4 + shadcn/ui (Radix primitives, "new-york" style, `src/components/ui`) + TanStack Query + Supabase (Postgres, Auth, Storage) + Vitest. `@lovable.dev/vite-tanstack-config` (imported in `vite.config.ts`) already wires up `tanstackStart`, `viteReact`, `tailwindcss`, `tsConfigPaths`, Nitro (Cloudflare build target), the `@` path alias, and error-logging/sandbox plugins — do not add duplicates of any of these manually. `vite-plugin-pwa` is configured separately in `vite.config.ts` for the offline/installable PWA behavior.

### Routing

File-based routing under `src/routes/` (see `src/routes/README.md` for the naming conventions: `$id` for dynamic segments, `{-$param}` for optional, `$` for splat, `_layout` for layout routes). `src/routes/__root.tsx` is the single app shell. `src/routeTree.gen.ts` is auto-generated by the TanStack router plugin — never hand-edit it. Authenticated pages live under `src/routes/_authenticated/`; that layout route (`_authenticated/route.tsx`) gates on `supabase.auth.getUser()` in `beforeLoad` and redirects to `/auth` if unauthenticated (`ssr: false` — auth state is client-only there).

### Server entry / SSR error handling

`src/start.ts` defines the TanStack Start instance with a global `errorMiddleware` (wraps request handling, renders a fallback error page on uncaught errors) and `attachSupabaseAuth` as a global function middleware (attaches the Supabase bearer token to every server-function RPC from the client side). `src/server.ts` wraps the generated Nitro/h3 server entry an extra layer deeper: h3 can swallow an in-handler throw into a bare 500 JSON body (`{"unhandled":true,"message":"HTTPError"}`) that bypasses normal try/catch, so `normalizeCatastrophicSsrResponse` detects that shape and re-renders the same error page (`src/lib/error-page.ts`) instead of leaking the raw JSON.

### Supabase integration

- `src/integrations/supabase/client.ts` — browser/SSR client using the publishable (anon) key, RLS-scoped. Exported as a lazy `Proxy` so env access is deferred.
- `src/integrations/supabase/client.server.ts` — service-role admin client that bypasses RLS. Only for trusted server-side code; import it dynamically (`await import(...)`) inside server function handlers, not as a top-level import, since route files and `*.functions.ts` files ship to the client bundle.
- `src/integrations/supabase/auth-middleware.ts` (`requireSupabaseAuth`) — server-side function middleware that validates the `Authorization: Bearer` header via `supabase.auth.getClaims`, and injects `{ supabase, userId, claims }` into handler context.
- `src/integrations/supabase/auth-attacher.ts` (`attachSupabaseAuth`) — client-side function middleware, registered globally in `src/start.ts`, that reads the current session and attaches the bearer token to outgoing server-function requests.
- `src/integrations/supabase/types.ts` — generated DB types (`Database`). These four files plus `types.ts` are marked "automatically generated" — treat them as generated artifacts, not hand-maintained code, even though there's no committed generator config in this repo.
- Server functions needing privileged DB access follow the pattern in `src/lib/*.functions.ts` (e.g. `account.functions.ts`): `createServerFn(...).middleware([requireSupabaseAuth]).handler(...)`, then dynamically import `supabaseAdmin` inside the handler.

### Data/domain layer

`src/lib/` holds the bulk of the domain logic as plain TypeScript modules (nutrition scoring, meal planning, shopping-list generation, points/ranks/achievements, portion scaling/unit conversion, cookbook PDF export, OpenFoodFacts lookups, etc.), consumed by React through custom hooks in `src/hooks/` (mostly thin TanStack Query wrappers, one hook per domain concern). Files ending `*.functions.ts` are TanStack Start server functions (bundled for both server and client — keep server-only secrets out of them, see above); files ending `*.server.ts` are server-only and safe for top-level secret imports. Validation schemas use `zod` (`src/lib/schemas.ts`).

### Database migrations

`supabase/migrations/` is an append-only, timestamp-ordered sequence of SQL migrations (Supabase project id in `supabase/config.toml`). Add new schema changes as a new timestamped file rather than editing past migrations.

### PWA

Configured via `vite-plugin-pwa` in `vite.config.ts`: service worker registration is handled by a custom wrapper (`injectRegister: null`), disabled in dev/Lovable preview. Workbox caching is deliberately routed by path: `/_serverFn/*` and `/api/*` are `NetworkOnly` (server-function RPCs and API routes must never be cached), HTML navigations are `NetworkFirst`, hashed static assets are `StaleWhileRevalidate`. Keep new runtime routes consistent with this split when adding server functions or API endpoints.

### Environment variables

`SUPABASE_URL` / `VITE_SUPABASE_URL` and `SUPABASE_PUBLISHABLE_KEY` / `VITE_SUPABASE_PUBLISHABLE_KEY` (client-safe anon key, read via `import.meta.env` on the client and `process.env` during SSR) and `SUPABASE_SERVICE_ROLE_KEY` (server-only, admin key — never expose to client code).
