# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

A German-language recipe/meal-planning PWA ("Rezepte") built with TanStack Start, React 19, and a self-hosted backend (Express + MariaDB on a Synology NAS, folder `nas-api/`). Originally created with [Lovable](https://lovable.dev); its hosted backend is no longer used (the build config still uses `@lovable.dev/vite-tanstack-config`). Avoid rewriting published git history (force-push, rebase/amend/squash of pushed commits) and keep the branch in a working state.

## Commands

- `bun run dev` — start the dev server (Vite + TanStack Start)
- `bun run build` — production build
- `bun run build:dev` — development-mode build
- `bun run test` — run the full test suite (Vitest, `run` mode — no watch)
- `bun run test -- src/lib/meal-plan.test.ts` — run a single test file
- `bun run test -- -t "test name"` — run tests matching a name pattern
- `bun run lint` — ESLint over the whole repo
- `bun run format` — Prettier write (100 print width, double quotes off, trailing commas)
- `bun run preview` — preview a production build

Package manager is Bun (`bun.lock`, `bunfig.toml`). `bunfig.toml` enforces a 24h supply-chain guard (`minimumReleaseAge`) on new dependency versions — only a short allowlist of `@lovable.dev/*` packages bypasses it; adding to that list needs explicit user confirmation.

## Versionierung und APK

Die App-Version steht nur in `package.json` (`"version"`, Schema MAJOR.MINOR.PATCH). Claude ist für die Versionierung zuständig und erhöht sie vor jedem APK-Build: PATCH für Fehlerbehebungen und Kleinigkeiten, MINOR für neue Funktionen (1.1.0 = Kühlschrank), MAJOR nur bei großem Umbau. Die gewählte Version wird dem Nutzer genannt. `bun run apk` übernimmt sie nach `android/app/build.gradle` (versionName, versionCode = MAJOR*10000 + MINOR*100 + PATCH), baut die Debug-APK und legt eine Kopie `NUTRI-<version>.apk` in `Downloads\Nutri-Projekt`. Installiert wird danach mit `adb install -r` aus `android/app/build/outputs/apk/debug/app-debug.apk`.

## Architecture

### Stack

TanStack Start (file-based SSR router on Vite/Nitro) + React 19 + TypeScript + Tailwind v4 + shadcn/ui (Radix primitives, "new-york" style, `src/components/ui`) + TanStack Query + our own NAS-API (Express + MariaDB, see below) + Vitest. `@lovable.dev/vite-tanstack-config` (imported in `vite.config.ts`) already wires up `tanstackStart`, `viteReact`, `tailwindcss`, `tsConfigPaths`, Nitro (Cloudflare build target), the `@` path alias, and error-logging/sandbox plugins — do not add duplicates of any of these manually. `vite-plugin-pwa` is configured separately in `vite.config.ts` for the offline/installable PWA behavior.

### Routing

File-based routing under `src/routes/` (see `src/routes/README.md` for the naming conventions: `$id` for dynamic segments, `{-$param}` for optional, `$` for splat, `_layout` for layout routes). `src/routes/__root.tsx` is the single app shell. `src/routeTree.gen.ts` is auto-generated by the TanStack router plugin — never hand-edit it. Authenticated pages live under `src/routes/_authenticated/`; that layout route (`_authenticated/route.tsx`) gates on `db.auth.getUser()` in `beforeLoad` and redirects to `/auth` if unauthenticated (`ssr: false` — auth state is client-only there).

### Server entry / SSR error handling

`src/start.ts` defines the TanStack Start instance with a global `errorMiddleware` (wraps request handling, renders a fallback error page on uncaught errors) and `attachAuth` as a global function middleware (attaches the bearer token to every server-function RPC from the client side). `src/server.ts` wraps the generated Nitro/h3 server entry an extra layer deeper: h3 can swallow an in-handler throw into a bare 500 JSON body (`{"unhandled":true,"message":"HTTPError"}`) that bypasses normal try/catch, so `normalizeCatastrophicSsrResponse` detects that shape and re-renders the same error page (`src/lib/error-page.ts`) instead of leaking the raw JSON.

### Backend (NAS-API)

The app no longer uses Lovable/Supabase. All data, login, files and the AI photo scan go through our own API in `nas-api/` (Express + MariaDB, Docker on the Synology NAS, reachable in the home network at `VITE_API_URL`, e.g. `http://192.168.0.30:3000`). See `nas-api/` for server code: `src/query.js` (generic select/insert/update/delete with embedded relations), `src/policies.js` (access rules, the former RLS policies), `src/rpc.js` (former Postgres functions), `src/auth.js` (login, JWT), `src/storage.js` (files), `src/photoScan.js` (Claude vision, billing).

- `src/lib/db-client.ts` — the client used by the app: `from().select().eq()…`, `rpc()`, `auth.*`, `storage.from()` (same call syntax as before, so domain code stays unchanged). Network failures become `{ data: null, error }` with `code: "network"` and are reported to `src/lib/api-reachability.ts`.
- `src/lib/api-reachability.ts` — "online" in this app means *the NAS answers* (OS network status AND API reachable), fed into TanStack Query's `onlineManager`. Offline-capable mutations (`src/lib/offline-mutations.ts`) retry on network errors, so they pause, survive restarts and are sent when the NAS is back. `OfflineBanner` shows the status. The whole query cache (except `OFFLINE_EXCLUDED_PREFIXES`) is persisted in IndexedDB (`offline-persistence.ts`), and `offline-sync.ts` warms planner history (8 weeks back, 2 ahead), profile data, recipes and images.
- `src/integrations/db/client.ts` — exports `db`, the typed client (`Database` types from `types.ts`; the type helper comes from `@supabase/supabase-js`, a **dev-only type dependency**, no runtime code).
- `src/integrations/db/auth-attacher.ts` (`attachAuth`) — client function middleware that attaches the bearer token to server-function calls (registered in `src/start.ts`).
- `src/integrations/db/auth-middleware.ts` (`requireAuth`) — server function middleware (Cloudflare Worker) that verifies the API's JWT (`JWT_SECRET`) and provides `{ db, userId, claims }`; the Worker cannot reach the NAS in a home-network-only setup, so server functions that need data are currently limited.
- `src/integrations/db/types.ts` — table types (`Database`), kept from the earlier generated file; update by hand when the schema changes.
- Open migration work (PDF export, cookbook share link, push, account deletion) is tracked in `ROADMAP.md`.

### Data/domain layer

`src/lib/` holds the bulk of the domain logic as plain TypeScript modules (nutrition scoring, meal planning, shopping-list generation, points/ranks/achievements, portion scaling/unit conversion, cookbook PDF export, OpenFoodFacts lookups, etc.), consumed by React through custom hooks in `src/hooks/` (mostly thin TanStack Query wrappers, one hook per domain concern). Files ending `*.functions.ts` are TanStack Start server functions (bundled for both server and client — keep server-only secrets out of them, see above); files ending `*.server.ts` are server-only and safe for top-level secret imports. Validation schemas use `zod` (`src/lib/schemas.ts`).

### Database schema

The schema lives in `nas-api/db/schema.mariadb.sql` (MariaDB) and `nas-api/db/schema.json` (column types/defaults/relations the API reads at runtime). Both were generated from the old Postgres dump with `nas-api/tools/convert_schema.py`. The 85 old Postgres migrations are archived in `nas-api/db/postgres-archiv/` for reference only. For a schema change: edit `schema.mariadb.sql` and `schema.json`, adjust `src/integrations/db/types.ts`, and apply the SQL on the NAS.

### PWA

Configured via `vite-plugin-pwa` in `vite.config.ts`: service worker registration is handled by a custom wrapper (`injectRegister: null`), disabled in dev. Workbox caching is deliberately routed by path: `/_serverFn/*` and `/api/*` are `NetworkOnly` (server-function RPCs and API routes must never be cached), HTML navigations are `NetworkFirst`, hashed static assets are `StaleWhileRevalidate`. Keep new runtime routes consistent with this split when adding server functions or API endpoints.

### Environment variables

`VITE_API_URL` (NAS-API address, read at build time; see `.env.example`). The API itself is configured in `nas-api/.env` (`DB_*`, `JWT_SECRET`, `ANTHROPIC_API_KEY`, see `nas-api/.env.example`). Never commit `.env` files, database dumps or the key file `nas-api/src/anthropic-key.txt`.
